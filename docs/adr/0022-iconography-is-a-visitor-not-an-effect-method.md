# Card iconography is a Visitor over the Effect AST, not a method on every node

> **Update.** The Visitor decided here still stands, but its population does not.
> The totality gate below is described as enumerating every node type by walking
> every registered card; a card walk reaches only the mechanics an implemented
> card happens to carry, which is roughly half the pool. The pass is now proved
> total against the engine's **node census** (ADR 0018) instead. The contract —
> which rows must draw, which may draw nothing, and what the card walk is still
> for — is stated in "Update: the population is the census, not the card pool" at
> the end of this file, which supersedes the totality paragraphs in Decision and
> Consequences.

## Context

A card's printed rules text is generated by `Text()`, an intrinsic method on
every `Effect` node that lives next to `Resolve()` (ADR 0006). Co-locating text
with behavior is the anti-drift guarantee: printed text can never desync from
what the card does. We now want a second rendering of the same mechanics — an
**Icon strip**, a thin band of composed glyphs that transcribes a card's effects
visually (`3 damage → enemy creature`), shown alongside the text. The obvious
question is whether iconography should follow `Text()` and become a third
intrinsic method on every node.

It should not, and the reason is not "text is identity, icons are not" — both are
identity. The discriminator is **locality of composition**:

- `Text()` composition is purely local string concatenation. Each node emits its
  own fragment; the parent joins fragments with commas, "and", or newlines. A
  node never needs to see a sibling to render its words, so a per-node method
  maximizes cohesion and a central view buys nothing.
- The Icon strip is inherently **cross-node and spatial**. Glyphs are squished,
  overlaid, and combined; a Target filter is folded into its verb's glyph as an
  edge decoration rather than taking its own slot. Emitting a good strip requires
  seeing neighbors, which per-node methods — each of which sees only itself —
  cannot do well.

AGENTS.md already draws this line: whole-tree operations that are not part of a
card's identity are a standalone type-switch function over `Effect` in one file,
the Go-idiomatic **Visitor**, never a third method on every node. Iconography is
such a pass.

## Decision

The **Iconography pass** is a Visitor that type-switches over the engine's
`Effect` AST and the strategies beside it, emitting the
glyphs the web client renders into the Icon strip. It is the visual counterpart
of rules-text generation and runs in the WASM client, so no pre-rendered card art
is ever served — every card's strip is generated in the browser from base glyph
assets.

The pass lives in the **client layer (`internal/web`), not in package `engine`**.
`internal/engine` is held at 100% coverage; an in-engine Visitor would force an
icon-specific engine test for every one of the effect AST's ~150 node types, and
every future effect would have to add an icon-test arm just to keep the gate
green — turning the anti-drift gate into a maintenance tax rather than a safety
net. `internal/web` is deliberately ungated (a view layer exercised through a few
entry points), and the effect types' fields are exported (cards are authored
through the `card` facade's aliases), so a type switch over `engine.Effect` reads
them fine from the client. The Visitor thus consumes the engine's AST without
living inside the gated package.

Co-location's anti-drift guarantee is replaced by an external one: a **totality
test** enumerates every node type and fails when any node yields the
unknown-glyph sentinel, so a mechanic that cannot be expressed visually fails
loud and early. (The test enumerated them by walking every registered card
(`cards.All()`) and rendering its strip; that population is superseded by the
census — see the Update at the end of this file.) A few example-bound
transcription tests
pin representative cards. There is deliberately **no golden snapshot** of every
card's strip: a snapshot only proves that something changed, never that the
change is wrong, and mass re-blessing invites brittleness and rubber-stamping.

The strip is a pure function of a `CardDefinition`, computed once and memoized per
definition in the web layer; live board state stays in the stat area. Because the
tokens never enter `GameState`, they are not bound by the engine's flat,
pointerless, comparable value rules (ADR 0005) — the token schema is chosen for
readability (a small nested value, glyphs carrying decorations and child glyphs),
not for MCTS snapshot performance.

## Consequences

- A new mechanic that should appear on the strip is a new arm in the Iconography
  Visitor, not a new method on the node — the same shape as other whole-tree
  passes.
- The totality test makes glyph coverage a build gate: adding an effect without a
  glyph mapping breaks `mage ci:check`, which is the intended "fail loud" behavior.
  The gate carries **no tolerance allowlist** — there is no map of node types
  permitted to fall back to the unknown glyph. Every effect must map to a real
  glyph (or, where a mechanic has no icon vocabulary at all, deliberately render
  nothing while reporting itself covered, as a trait grant does — traits are card
  text, not strip glyphs). An unmapped node is always a failure to fix, never one
  to silence. Which nodes may render nothing is no longer a judgement the client
  makes: the census's `NoTerm` reason decides it — see the Update at the end of
  this file.
- Coverage is checked at **both** ends of a line: `TestNoResidualUnknownGlyph`
  scans a card's rendered strip for the unknown sentinel in its trigger-head
  glyph as well as its effect-body glyphs, so a new trigger with no icon mapping
  fails the same way a new effect does.
- The strip complements the rules text and never replaces it; if the strip
  cannot fit or a glyph is missing, the text remains the lossless source of
  truth.

## Update: the population is the census, not the card pool

The Decision above proves the pass total by walking every registered card. That
population is wrong in both directions. It is too small: a card walk reaches only
the mechanics an implemented card happens to carry, which is roughly half the
pool, so an effect node with no glyph passes the gate until the card that uses it
is written. It is also mis-aimed: nothing in the icon files reads an
`engine.Count` or an `engine.Condition` at all, so the claim that the pass
type-switches over those strategies described an aspiration rather than the code.

The population is now the engine's **node census** (ADR 0018), which is complete
by construction: a node the package declares and the census does not list fails
the engine's own build, so a population drawn from the census cannot be behind
the engine.

### The census is the population

The pass is proved total against the fifteen typed catalog accessors —
`EffectCatalog()`, `ConditionCatalog()`, `CountCatalog()`,
`RefinementCatalog()`, `SelectionCatalog()`, `SpreadCatalog()`,
`TopActCatalog()`, `PerTargetCatalog()`, `LossCatalog()`,
`RepeatGateCatalog()`, `QuantityCatalog()`, `GatherCatalog()`,
`BonusIconSubjectCatalog()`, `CreatureVerbCatalog()`,
`TargetFilterCatalog()` — and the text-bearing value enums beside them
(`Enums()`). The typed accessors are read directly rather than through
`Families()`, because `Family.Rows` erases a node to its type name and the pass
needs the node itself to draw it.

The enums are part of the contract but not of the harness, and for the same
reason: an `Enum`'s rows are already erased to `FamilyRow`, so no value survives
for the pass to draw. Each is drawn through the node that carries it — a
`Duration` through the effect it wraps, a `Destination` through the zone move —
so an enum member with no picture shows up as its carrier's strip saying too
little, not as an unclaimed row.

Each family carries a gating switch, in the spirit of `Family.Gated`: a family
whose glyphs are not drawn yet is reported but does not fail the build, and the
change that draws a family flips its switch. A sixteenth accessor added to the
engine fails the harness, so the family cannot arrive without an icon decision.

### Drawing is tied to teaching, and the engine holds that judgement

A census row carries a mandatory `RulesBearing`, and that classification decides
what the row owes the strip:

- A row whose `Rules` names a `Term` teaches a player a word. It **must draw a
  real glyph, and must draw a distinct one** — the collision gate applies to it.
- A row whose `Rules` names a `NoTerm` is plumbing. It **may draw nothing**,
  folding into its children, which is exactly what `icon_compose.go` already does
  for `Sequence`, `Then`, `ForEach`, `Repeat` and the duration wrappers.

No allowlist lives in `internal/web`. The reason a node draws nothing is recorded
in `internal/engine`, beside the reason it teaches no rule, so the two judgements
cannot drift apart and neither can be made twice. Across `Effect`, `Condition`,
`Count` and `TargetFilter`, `Silent` never co-occurs with a `Term`, so the rule
needs no exception clause for a rule-bearing node that prints nothing.

### The abstract unknown glyph is not part of the contract

`fallbackGlyphs` and `glyph-unknown` are scaffolding for the work of drawing the
families, not a picture a player is meant to see. Once every rule-bearing row
draws, an unmapped node is a **build failure**, not a glyph.

### The card walk survives, and this is why

The card walk stays as a **second population**, not a replacement, and deleting
it as redundant would lose two things the census cannot give:

- It is the only population that reaches `cardGlyphs` — keywords,
  `FightRestriction`, `DrawModifier`, `Static` bonuses, `Restricts`, `Replaces`,
  `KeyCostChanges`, `ConstantAbilities`, and the trigger heads. None of those is
  an `Effect`, so no effect catalog row reaches them.
- It is the only population that reaches **composed shapes** — a
  `ChooseHouseThen` wrapping a granted ability, a `Conditional` over a nested
  sequence — which a bare catalogued node, filled only as far as it needs to
  render, never forms.

### The Target filter family is deferred

`TargetFilterCatalog()` is catalogued but not yet drawn. Its axes are unexported
fields on `engine.Target`, so the pass cannot read the filter a row applies, and
drawing it would mean re-deriving the filter from its rendered text. It is drawn
once the `replace-target-s-filter-methods` goal replaces those methods with a
comparable exported `engine.Filter`; this work waits on that goal rather than
building a reader for a shape that is about to change.

The glyph families and the `decor` / `sigil` axes the drawings are composed from
are ADR 0047's, unchanged by this update.
